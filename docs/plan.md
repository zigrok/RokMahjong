# Rok Mahjong — Implementation Plan

**Status:** planning approved. Implementation starts at milestone M0.
**Working title:** Rok Mahjong.
**Default theme:** Jade Garden (proposal; Tea House and Midnight Lotus remain alternatives).

> **Live progress:** this plan is checklist-driven. Run
> `./tools/plan-progress.sh docs/plan.md` for status. Mark work in progress with
> `- [~]` and complete it with `- [x]` in the **same change** that does the work.
> The desktop goal prompt uses the M0–M5 phases and the
> **Desktop v1 acceptance** checklist as its completion gate.

> **Desktop v1 delivery note:** the first playable build uses C# Forma
> controls (FHTML authoring is deferred), vector 2.5D tiles (the texture atlas
> is deferred), and a pure headless gameplay harness through the real input
> router and board controller (the native MonoGame `desktopheadless` backend is
> deferred). Gameplay, input, save/resume and solvability are implemented and
> tested; deferred polish is tracked in the Post-v1 backlog below.

Rok Mahjong is a relaxing mahjong solitaire matching game built with the
`zigrok/MonoGame` fork and the `zigrok/Forma` UI toolkit. It targets desktop first,
with a responsive layout and an input model designed for portrait/landscape,
touch, mouse, keyboard and controller from the beginning.

---

## 1. Locked decisions

- **Platforms:** desktop first (macOS / Windows / Linux); Android/iOS is a later
  Forma mobile workstream. Everything is touch-sized and input-abstracted now.
- **Rules:** classic mahjong solitaire first. Vita's 4-slot tray becomes a second
  mode after v1.
- **Content:** three layout families, 12 handcrafted levels, free play, hint /
  undo / shuffle.
- **UI:** Forma. Desktop v1 uses C# Forma controls; FHTML/FCSS views are a
  post-v1 migration. The board is a C# `DrawingElement`.
- **Art:** original generated vector tile art, baked into a 2.5D atlas.
- **Upstream:** Forma and MonoGame may be extended where needed. Changes are
  developed on feature branches, validated by their own CI, and merged through
  pull requests.
- **Rotation:** new games pick the best layout for the current aspect ratio.
  Mid-game rotation auto-fits the board and prompts if tiles fall below the touch
  minimum. The board and history are never silently re-dealt.

## 2. Product shape

A calm, large-tile matching game in the spirit of Vita Mahjong:

- Default mode has **no timer and no score pressure**, while still showing score
  and combo.
- **Tap two free matching tiles**, or **drag one tile onto its match**.
- A tile is free when nothing covers it and at least one long side is open.
- Assists: **hint**, **undo**, **shuffle**, **restart**.
- A 12-level journey with 1–3 stars, level select, best score and resume.
- One polished theme at launch; the theme system is ready for more.
- Post-v1: 4-slot tray mode, daily challenge, special tiles, more layouts,
  additional themes and localization.

## 3. Visual direction: Jade Garden

A 2D presentation with **2.5D tiles**:

- Ivory tile face, warm bevel, visible right/bottom thickness, baked soft shadow.
- Higher layers offset up-left; painter's order is `z → y → x`.
- Selected tile lifts and glows; hints pulse; matches sparkle; invalid moves shake.
- Deep jade felt, subtle vignette, drifting light particles, warm wood panels.
- Reduced-motion mode removes particles, deal stagger and shake, keeping short
  fades.
- Tile symbols use the traditional palette: ivory, red, green, blue and gold.

The tile set contains all 42 traditional faces:

- 9 circles, 9 bamboo, 9 characters, 4 winds, 3 dragons, 4 flowers, 4 seasons.
- Flowers match flowers; seasons match seasons.
- The art is generated by a C# + SkiaSharp tool and checked in as a PNG atlas, so
  runtime builds do not need the art tool.

Facets of the theme are data/tokens, not hard-coded in views. Additional themes
(Tea House, Midnight Lotus) can replace the palette, felt, UI surface and tile
body colors without touching gameplay code.

## 5. Core rules and data model

`RokMahjong.Core` owns all game rules and is deterministic.

### Coordinates

- Tile positions are **half-tile units**: `(x, y, z)`.
- A tile occupies `[x, x+2) × [y, y+2)`.
- Overlap: `|dx| < 2 && |dy| < 2`.
- Covered: any tile on a higher layer overlaps.
- Side-blocked: same layer, overlapping row, and touching at `dx = ±2`.
- Free: not covered and not blocked on both left and right.

### Main types

```csharp
record struct TileCoord(int X, int Y, int Z);
enum MatchGroup { Characters, Bamboo, Circles, Wind, Dragon, Flower, Season }
readonly record struct TileFace(MatchGroup Group, int Rank, string ArtId);
sealed class Tile;
sealed class BoardLayout;       // slots + metadata + preview
sealed class MahjongGame;       // tiles, selection, history, status
sealed class DealGenerator;     // backwards solvable deal
sealed class ShuffleService;    // solvable reshuffle of remaining faces
sealed class HintService;
sealed class ScoreTracker;
```

### Solvable deals

Backwards generation:

1. Start with every layout slot occupied.
2. Build the deck's pair units (regular faces and flower/season groups).
3. Shuffle pair units.
4. Repeatedly pick two currently free slots at random, assign the next pair,
   mark them removed.
5. Retry if fewer than two free slots remain.
6. Verify the stored removal order replays to an empty board.

A wrong player choice can still create a dead end. Deadlock detection checks
whether any free matching pair remains and offers shuffle / undo / restart.

### Layout families and sizes

Three families, with size variants to keep early levels friendly:

| Family | Shape | Sizes | Best for |
| --- | --- | --- | --- |
| **Lotus** | compact, portrait-friendly | 36, 72 | tutorial / phone |
| **Pagoda** | tall, 8-column | 72, 108, 144 | portrait / tablet |
| **Turtle** | classic wide | 144 | landscape / desktop |

Layouts are data (`layouts/*.json`) so they can be validated and previewed.
Level definitions (`levels.json`) reference a layout, deck size, seed, title and
star rules.

Deck profiles:

- **Mini36:** 18 faces × 2 copies.
- **Classic72:** 18 faces × 4 copies.
- **Classic108:** 25 faces × 4 copies + flowers/seasons.
- **Classic144:** 34 faces × 4 copies + 4 flowers + 4 seasons.

### History

- `MatchMove`: two tile IDs.
- `ShuffleMove`: previous face assignment for all remaining tiles.
- Undo restores the last entry, including shuffle.
- Restart clears history.
- Selection is UI state, not history.

### Scoring and stars

- Base points per pair + combo multiplier (up to ×5) + clear bonus.
- Invalid match resets combo.
- 3 stars = no hints/shuffles/undos; 2 stars = at most one assist; 1 star =
  complete.
- Best score per level persisted.

## 6. Responsive board and orientation

### Fit algorithm

The board computes a uniform scale from the available rectangle:

- Tile aspect ratio ~0.75 (width / height).
- Layer depth offset ~18% of tile width; side thickness ~10%.
- Board bounds include shadow/side margins.
- `tileWidth = min(availableWidth / normalizedWidth,
  availableHeight / normalizedHeight)`.
- Center the board and clamp tile width to a maximum so art stays crisp.
- Minimum touch width: **44 logical units** on touch devices, slightly lower on
  desktop.
- If the fit drops below the minimum, show a friendly overlay:
  - "This board is better in landscape."
  - Actions: rotate guidance, **Restart with [portrait layout]**, or keep
    playing.

### Layout selection

- On new game, score each allowed layout by resulting tile size, orientation
  match and level constraints.
- Portrait: prefer Lotus/Pagoda.
- Landscape: prefer Turtle/Pagoda.
- Tablet/square: best fit by aspect ratio.

### Mid-game rotation

- Keep the logical board and history.
- Recompute presentation on resize/orientation change.
- If the layout still fits above the minimum, continue seamlessly.
- If not, prompt; never silently re-deal or lose progress.

## 7. Board rendering

### Tile atlas

A build-time tool renders one atlas with:

- 42 tile cells. Each cell is an **axis-aligned 2.5D extrusion**: the top face
  is a perfect rounded rectangle (vertical and horizontal edges only), and the
  right and bottom sides are a shaded band inside the same tile footprint. No
  perspective, no camera skew.
- The flat top face carries the face texture: an RGBA glyph from the pipeline,
  a retained legacy painted face, or the vector symbol as a fallback.
- A height field (supplied as `<label>.height.png` or derived from the glyph
  alpha) bumps the glyph, so the symbol picks up real relief shading.
- The tile silhouette is fit to the logical tile bounds, so the bevel and side
  stay inside each tile slot on a packed board.
- Metadata JSON: cell rect, face rect, depth margins, base size.
- Mipmapped, premultiplied alpha.
- 6×7 cells at 256×340, with room for a second theme later.

The atlas builder is deterministic and CPU-only, so `make tiles` needs no GPU
and the atlas stays reproducible.

At runtime each tile is **one `DrawImage` call** with a transform. Selection,
hint glow, drag highlight and particles use a small number of vector paths on top.

### Tile face generation pipeline

`tools/tile-pipeline` is a local-first Python CLI that generates, keeps and
selects tile face art.

- `assets/art/reference/<label>.png` — body-less vector reference art, emitted
  by `make tiles`, used as the structure image for every generation.
- `roktiles generate` sends a face to ComfyUI (Qwen-Image-Edit 2511 GGUF by
  default), to Qwen-Image-Layered for a transparent glyph, or to an OpenRouter
  image model.
- Every generation is stored under `artifacts/tile-pipeline/history/` with a
  SQLite index of prompt, negative prompt, seed, model and parameters.
  `artifacts/` is gitignored, so history never bloats the repository.
- `roktiles sheet --face <label>` renders a labelled contact sheet so
  candidates can be compared without a GUI.
- `roktiles select <generation>` writes the chosen art into
  `assets/art/glyphs/` (RGBA glyph + derived height map, for transparent
  layered output) or `assets/art/faces/` (retained painted faces), records a
  provenance manifest and rebuilds the atlas.
- `roktiles reset` drops a face back to the vector fallback.
- Style presets (`porcelain`, `lacquer`, `ink`, `jade`, `enamel`, `minimal`)
  change the look only; the per-face subject sentence protects glyphs and pip
  counts.

Selected faces and `assets/art/faces/manifest.json` are committed, so the game
builds from the chosen art without ComfyUI, Python or the history database.

### Draw order and effects

- Sort remaining tiles by `z`, then `y`, then `x`.
- Draw the board mat, then tiles, then overlays/particles.
- Deal-in: staggered scale/fade from above.
- Select: lift + gold outline + slight scale.
- Match: pulse, sparkles, ghost fade-out.
- Invalid: horizontal shake + muted flash.
- Hint: pulsing glow + dashed connector between the pair.
- Shuffle: crossfade/redistribute.
- Combo popup at the last match position.
- Reduced motion keeps only short fades.

### Board as a Forma control

`MahjongBoardView : DrawingElement`:

- Draws in global UI coordinates using `DrawingContext`.
- Uses `PointerPressed/Moved/Released` for hit testing and gestures.
- Exposes `FocusTile`, `SelectFocused`, `ClearSelection`, `PeekTile`, plus the
  layout/presentation API.
- Board-local hit testing uses the top face rectangle, iterating topmost-first.

Performance target: 144 tiles well under 16 ms on desktop and mobile-class
hardware; no per-tile path tessellation in the hot path.

## 8. Input model

A single `InputRouter` reads all devices and produces an `InputSnapshot`:

- Mouse (desktop)
- Touch (`TouchPanel` on native mobile; browser later)
- Keyboard
- Gamepad (up to 4; player one is used by default)

It tracks the **last used device** and sets `UIContext.InputModality`
(`Pointer`, `Touch`, `Keyboard`, `Gamepad`) so prompts and adaptive styles update.

### Routing

- All pointer/touch input is injected into Forma via
  `InjectPointerMove/Press/Release`; the game sets `SuppressPolledInput = true`
  and owns the update loop.
- Keyboard/gamepad input is injected into Forma for menus and HUD focus, or
  dispatched directly to the board during play.
- Gamepad maps to abstract actions, not raw keys:
  `Navigate*`, `Accept`, `Cancel`, `Hint`, `Shuffle`, `Undo`, `Pause`.
- D-pad repeats after an initial delay; the left stick has a deadzone and
  acceleration.

### Gameplay bindings

| Action | Mouse / touch | Keyboard | Gamepad |
| --- | --- | --- | --- |
| Select / match | click/tap, or drag | Enter / Space | A |
| Move tile cursor | hover / direct | arrows / WASD | D-pad / left stick |
| Cancel selection / back | right-click / tap empty | Esc | B |
| Hint | toolbar | H | X |
| Shuffle | toolbar | S | Y |
| Undo | toolbar | U / Z / Ctrl+Z | LB |
| Pause | toolbar | Esc | Start |
| Focus HUD | click | Tab | RB / D-pad to HUD |

- Touch adds **long-press to peek** at a partially covered tile and
  **drag-to-match**.
- Gamepad tile navigation moves between free tiles by projected direction; a
  visible focus ring shows the target.
- Input prompts show the active device's glyphs (Kenney CC0 prompt assets, as
  used by Trace Arena).

### Forma keyboard hook

Small upstream Forma change:

- Make `Control.KeyPressed` / `KeyReleased` `protected internal` (and optionally
  `PointerEntered` / `PointerExited`) so a custom `DrawingElement` can participate
  in focus and keyboard input like any other control.
- Add tests that a board-like custom control can receive keys through
  `UIContext`.

This avoids duplicating focus logic in the game.

## 9. UI: Forma

### Structure

- `RokMahjongGame` owns one `UIContext`, the embedded font family, display
  scale, input injection and disposal.
- `GameShell` owns the screen stack and gameplay state.
- **Desktop v1 uses C# Forma controls.** FHTML/FCSS authored views and Debug
  hot reload are tracked in the Post-v1 backlog.
- The theme is a `Forma.Theme` token set: jade surfaces, ivory text, gold
  accents, spacing and focus colors.
- The board is a C# `DrawingElement`; the HUD and menus are Forma controls.

### Screens

1. Main menu
2. Level select (12 cards with mini layout previews, stars, locked states)
3. Gameplay HUD (top bar + action bar/side rail)
4. Pause
5. Settings
6. How to Play (illustrated free-tile rule)
7. Win / result
8. Deadlock prompt
9. Confirm dialog (restart/quit)

### Design tokens

- Colors: deep jade, warm ivory, muted ink, gold accent, coral danger.
- Spacing scale: 4 / 8 / 12 / 16 / 24 / 32.
- Radii: 8 / 12 / 16; tile radius ~10% of width.
- Motion: 120 / 180 / 260 ms with shared easings; reduced-motion variants.
- Typography: warm serif for titles, humanist sans for body; one body size,
  weight for emphasis.
- Every interactive control gets an `AutomationId` and accessible name.

### Responsive UI

- C# computes a breakpoint: compact portrait, compact landscape, medium,
  expanded.
- The board and bars are arranged explicitly by the shell; each bar is a C#
  Forma container with its own horizontal layout.
- The board fit adapts to portrait and landscape rectangles; the action bar
  stays horizontal in v1 and is a post-v1 refinement for very short windows.
- The HUD exposes the current input shortcuts in the How to Play screen.

### Fonts

- Desktop: Forma DynamicText with embedded OFL fonts (serif title + sans body).
- Mobile phase: validate DynamicText; if native FreeType/HarfBuzz assets are not
  viable, switch to SpriteFont with the same metrics. One abstraction, no
  duplicate layout code.

## 10. Content, audio, persistence

### 12-level journey

- Levels 1–3: Lotus 36, tutorial pacing.
- Levels 4–6: Lotus 72 / Pagoda 72.
- Levels 7–9: Pagoda 108.
- Levels 10–12: Turtle 144.
- Each level: fixed seed, title, layout, deck, star rules, optional assist limits.
- Free play: choose any unlocked layout and deck size.

### Audio

- Ambient loop: water, birds, soft wind.
- SFX: tile pick, match clack + chime, invalid thud, shuffle rustle, hint chime,
  win gong, UI click.
- Combo matches raise pitch slightly.
- Music/SFX volume settings persisted; optional mute on focus loss.
- Start with curated CC0 assets; generate temporary placeholders where needed.

### Persistence

- JSON in the platform app-data folder, atomic writes, schema version and backup.
- Stores: settings, progress/stars/best scores, current session (for Continue),
  first-run tutorial flag.
- Auto-save after each move, on pause and on exit.
- Seeded deterministic RNG, so a saved game resumes exactly.

## 11. Testing and verification

The full strategy is in [`docs/testing.md`](testing.md). The plan commits to
testing the **real game**, not only the model:

### Quality goals

- Every generated deal and shuffle is **completable** under the exact rules the
  game uses.
- A solver-driven agent clears boards through the **real input path**: pointer,
  touch, keyboard and gamepad.
- Rule, input, UI, save and visual regressions are caught before release.
- Every failure is reproducible from a seed, scenario and replay file.
- Any automated scenario can be **watched** in a real window when desired.

### Test layers

| Layer | Scope | Runs |
| --- | --- | --- |
| **L0 Core** | Free rule, layouts, deals, history, scoring, serialization | Every commit, no GPU |
| **L1 Solvability** | Stored-solution replay, shuffle replay, oracle solver, invariants | Every commit |
| **L2 Forma headless UI** | Menus, focus, dialogs, layout, accessibility | Every commit, no GPU |
| **L3 MonoGame headless gameplay** | Real game loop, input router, board, Forma, save/resume | Every PR, headless backend |
| **L4 Windowed visual** | Screenshots, gallery diffs, recordings | PR/nightly, real backend |
| **L5 Soak/perf** | Large seed sweeps, long sessions, frame budgets, mutation | Nightly/release |

### Determinism

- Seeded RNG only; no wall clock in Core.
- `Game.StepFrame(elapsed)` drives exactly one update and one draw, with no
  sleeping or catch-up.
- One `IInputSource` per frame feeds both the board and Forma injection, so a
  test cannot pass by bypassing real input.
- Scenarios are `layout + deck + seed + actions + assertions`; failures log the
  seed, state hash, input transcript and UI tree.
- The same scenario runs headless for assertions and windowed for observation.

### Proving boards are playable and completable

1. **Generator guarantee:** the backwards dealer stores a removal order.
2. **Rule-agreement replay:** replay that order through `MahjongGame` and assert
   every pair is free, matches, and removes; finish with a Win result. Run for
   every layout/deck and at least 10,000 seeds (larger nightly sweep).
3. **Shuffle guarantee:** rebuild remaining pair units, assign them backwards,
   store the order, replay it through the current game state.
4. **Oracle solver:** independent DFS with a transposition table for small boards
   and sampled states; results are `Solved`, `Deadlocked` or `Inconclusive`.
5. **Deadlock/hint agreement:** the detector and hint service must agree with
   legal-pair enumeration.
6. **Solver-driven input agent:** choose a verified move, then perform it through
   real pointer/touch/keyboard/gamepad actions until the Win screen appears.
7. **Invariants after every move:** even face counts, history consistency, undo
   state hash, shuffle multiset, save/load hash, free-set monotonicity.
8. **Seeded property-style tests** over random layouts, move sequences,
   undo/redo, save points and viewports.
9. **Post-v1 mutation testing** for the critical Core rules (Stryker.NET).

### Headless gameplay harness

- Desktop v1 uses a **pure headless gameplay harness**: `ScriptedInputSource` →
  real `GameInputRouter` → real `BoardController` → `MahjongGame`. It needs no
  window, GPU or native runtime.
- `RokMahjong.Game.Tests` runs this harness for all 12 levels and all four
  input devices, plus a Forma `HeadlessInput` UI flow test.
- The native MonoGame `desktopheadless` backend and `Game.StepFrame` integration
  are tracked in the Post-v1 backlog. The v1 harness still uses the same input
  router and board code as the running game.
- Headless tests assert state, never pixels. The windowed gallery covers pixels.
- `RokMahjong.Playtest` runs the same solve headless and prints a JSON result;
  `--screenshot` on the desktop host captures visible proof.

### Seeing a test

The `RokMahjong.Playtest` CLI runs the same scenarios outside xUnit:

```bash
# Solve a level headless and print a JSON result.
dotnet run --project tools/RokMahjong.Playtest -- --level 1 --device mouse

# The same board in a real window.
dotnet run --project src/RokMahjong.Desktop
```

The desktop host also supports deterministic screenshots:

```bash
dotnet run --project src/RokMahjong.Desktop -- --screenshot artifacts/gallery/game.png --screen game
```

The v1 Playtest tool is a headless state harness, not a video recorder. The
windowed host is the visual proof; the gallery script captures menu, level
select, gameplay, settings and how-to-play screens.

### Visual regression

- Real-backend gallery scenes: main menu, level select, gameplay portrait,
  gameplay landscape, pause, settings, how-to-play, win, deadlock.
- Reference viewports: phone portrait/landscape, tablet, 1280×720, 1920×1080,
  2× scale.
- Baselines checked in; diffs and overlays uploaded as artifacts.
- Animations covered by short recordings, not single frames.
- Visual tests answer “does it look right?”; gameplay tests answer “does it play
  right?”.

### CI gates

- **Fast:** build + L0/L1/L2 on every push/PR.
- **Headless gameplay:** build/cache the headless runtime, run L3 + scenarios on
  every PR.
- **Visual:** windowed gallery on PR/nightly with baseline diffs.
- **Nightly:** 10k deal sweep, solver states, soak, performance and mutation.
- Failed jobs upload TRX, replay JSON, state dumps, UI trees, screenshots and
  recordings.
- No retries to hide flakiness; deterministic seeds and `StepFrame` remove most
  timing variance.

### Manual QA

Still required for feel: input comfort, animation polish, audio mix, device
ergonomics, rotation and first-run flow. Manual QA is listed per milestone.

## 13. Upstream changes

### Forma

- Custom-control keyboard hooks (`KeyPressed` / `KeyReleased` protected
  internal).
- Tests for custom focusable drawing controls.
- Use the existing `Forma.Testing` / `HeadlessInput` package for L2 UI tests;
  upstream fixes only if a gap blocks the board or scenario harness.
- Phase 2: mobile TFM/build support, GLES validation, safe-area/touch helpers if
  needed.
- No fork of Forma's rendering model; the board uses the public
  `DrawingContext`.

### MonoGame fork

- Use the existing `Game.StepFrame` and headless backend for deterministic
  gameplay tests; no fork change is required for v1.
- Desktop v1 otherwise needs no fork changes beyond using `AllowHighDpi` and the
  existing input stack.
- Phase 2: only if Android/iOS safe-area, orientation or activity lifecycle gaps
  appear.

### Process

Every upstream change follows the submodule workflow in `CONTRIBUTING.md`:

1. Create a feature branch inside the submodule.
2. Validate with the upstream repository's own checks and the game build/tests.
3. Push the branch and open a PR against the upstream default branch.
4. Wait for upstream CI to pass and merge.
5. Update the game repository's submodule pointer to the merged commit in a
   separate, clearly labeled commit.

## 14. Main risks and mitigations

| Risk | Mitigation |
| --- | --- |
| Forma has no native mobile validation | Desktop-first plan; M6 spike; SpriteFont/bitmap fallback; browser build as an alternate mobile path |
| Per-frame vector tessellation too slow | The v1 board uses cached unit paths and a small number of fills per tile; the texture atlas is the post-v1 optimization if profiling demands it |
| Gamepad navigation feels clumsy on 144 tiles | Free-tile spatial cursor, visible focus ring, hint moves cursor, stick as virtual pointer |
| Rotation mid-game makes tiles too small | Orientation-specific layouts, auto-fit, explicit prompt, no silent state loss |
| Unsolvable deals/shuffles | Backwards generator + rule-agreement replay through the real game; shuffle retry; deadlock detection |
| Tests pass but real input fails | One `IInputSource` feeds both the board and Forma injection; solver agent uses real pointer/keyboard/touch/gamepad actions |
| Headless runtime build is slow/fragile | Cache by MonoGame/native commit; dedicated headless job; fast tests stay GPU-free; document the SDL dummy-driver setup |
| Headless cannot see pixels | Separate windowed gallery and recordings; headless assertions are state-only by design |
| Solver too slow on 144 tiles | Stored generator/shuffle solutions for full boards; oracle on 36/72 tiles and sampled states with a budget |
| Scenario DSL drifts from the real game | DSL only emits input actions and assertions; it never mutates `MahjongGame` directly |
| Visual baselines flaky across GPUs | Pin the baseline OS/backend; use diff thresholds; review baselines on the same runner image |
| Flaky tests hidden by retries | Deterministic seeds + `StepFrame`; non-parallel headless collection; quarantine and fix, never retry-to-green |
| Save corruption / interrupted mobile suspend | Atomic writes, versioned schema, backup, save on pause/deactivate |
| Scope creep (tray, special tiles, daily) | v1 is classic only; `IMatchRule`/`TileBehavior` seams left for later modes |
